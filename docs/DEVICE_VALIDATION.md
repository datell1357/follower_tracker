# 기기·SNS 검증 기록

빌드와 합성 데이터 검사는 완료된 범위만 [구현 기록](WORK_LOG.md)에 기록한다. 2026-10-02에 Android Instagram의 실제 전경 자동 연결에 이어, API 36 에뮬레이터에서 앱 화면을 닫고 약 1분 간격의 수집과 홈 화면 위젯 반영을 확인했다. 이 결과는 알림이 있는 빠른 추적 모드의 짧은 관찰이며 일반 예약·실기기 절전·장시간 결과와 구분한다. 이후 첫 전체 명단 수집과 맞팔 비교를 확인했으며 실제 관계 변경과 다른 SNS는 별도 미검증 상태다.

2026-10-03에는 같은 에뮬레이터에서 약 6시간의 자체 상한 종료와 이후 60분 일반 예약의 새 수집·위젯 반영을 확인했다. 후속 관찰의 기기 조회 오류와 공백은 별도로 기록했다. 실기기·24/72시간·실제 iOS 세션과 위젯의 검증은 계속 남아 있다.

앱 복귀 시 위젯을 다시 그리는 작업은 기기에 저장된 기록만 읽으며 SNS에 새 수집 요청을 보내지 않는다. 2×2 크기 힌트가 있어도 시험 런처의 실제 배치는 2×3이었다. 크기 힌트만으로 원하는 셀 배치나 다른 런처 지원을 확인했다고 기록하지 않는다.

최종 Debug·테스트 APK 및 Release(R8) 빌드, HTTP 단위 검사 7개, debug/release lint가 통과했다. lint는 오류 0개와 기존 UseKtx 제안 3개다. 같은 기기에서 앱 화면·작업 취소·Intent 반복 전달 5개와 위젯 RemoteViews 6개, 총 11개 런타임 검사가 통과했다. Intent 검사와 별도로 실제 홈 화면 클릭 결과를 확인했다. 최종 Debug APK SHA-256은 `1285413302946e4a5de0da3c8c4e1c248abd543d270a60c0f0d1d88b96bebabc`다. 합성 위젯 수치를 앱 DB에 저장하지 않았다.

첫 APK 갱신 때 Glance의 패키지 갱신 Receiver 시작 중 앱 ANR이 발생했고, Cold Boot 때 System UI와 Google Play services의 ANR도 발생했다. 이후 빌드·설치·검사를 순서대로 실행했지만 초기 실패의 원인이 앱 코드에서 해결됐다고 판정하지 않는다. 관련 로그와 화면을 로컬에 보존했으며, 이번 결과를 안정적인 기기 재시작이나 실기기 백그라운드 수집의 증거로 사용하지 않는다.

Reddit의 계정 인증 전 세션 후보 쿠키 발급도 관측했다. 쿠키 존재는 로그인 성공으로 기록하지 않는다. 진단은 입력값·쿠키 값·DOM 원문을 저장하지 않으며 로컬 결과는 `.local/evidence/login-2026-10-01/official-login-pages-final.json`에 있다. 테스트 뒤 사용자가 직접 로그인할 수 있도록 독립 에뮬레이터에서 앱을 실행해 두었다.

본인 계정의 로그인은 앱 안의 공식 SNS 페이지에서 사용자가 직접 진행한다. 비밀번호·쿠키·원시 명단은 채팅이나 저장소에 전달하지 않는다. 실기기 종류와 시험할 SNS가 정해지면 아래 순서로 결과를 기록한다.

1. OS·앱·WebView 버전, SNS 계정 유형과 익명 시험 식별자를 기록한다.
2. 공식 화면에서 자기 계정을 확인한다. Android·iOS 모두 로그인 후 정확한 본인 수치를 확보하면 자동으로 연결한다. iOS의 현재 검증은 합성 WKWebView 검사이며 실제 계정 연결은 미검증이다. 정확한 수·수집 시각을 같은 시점의 공식 화면과 비교한다. 축약 수를 정확한 정수로 바꾸어 기록하지 않는다.
3. 연결 창을 닫고 앱에서 수 수집을 다시 실행한다. 다른 프로필, 로그인 만료, 확인 화면, 응답 변경이 마지막 정상 기록을 덮어쓰지 않는지도 확인한다.
4. 작은·중간·큰 홈 화면 위젯을 추가하고 표시 계정을 선택한다. 앱의 저장값·시각·상태와 비교하고 위젯을 눌러 앱이 열리는지 확인한다.
5. 앱을 열지 않은 상태에서 실제 새 수치가 관측되는지 확인한다. 예약 요청 시각, 실제 요청 시각, 위젯 표시 시각을 구분한다. 전경 수집 경로는 전경 전용으로 기록한다.
6. 앱 재실행·기기 재시작·화면 잠금·네트워크 단절과 복구·절전 상태를 검사한다. iOS에서는 서명된 앱·위젯의 App Group·Keychain 공유도 확인한다.
7. 대상 SNS 연결을 해제하고 그 SNS의 세션·기록만 제거되는지, 다른 SNS와 늦게 완료되는 요청에 영향이 없는지 확인한다.

## 관계 명단

Instagram 후보 경로에서 한 페이지를 넘는 명단을 읽고 정상 커서 종료·중복 제거·계정 일치·필터링 여부를 확인한다. 시작과 종료의 수가 같아도 동시점 스냅샷임을 증명하지는 않으므로 비원자적 수집으로 기록한다.

참여자가 동의한 시험 계정의 수동 관계 변경으로 맞팔의 두 방향, 첫 스캔 기준 생성, 이탈 후보, 다음 정상 스캔에서의 연속 미관측을 확인한다. 앱이 계정 삭제·비활성화와 실제 언팔로우 원인을 구분했다고 보고하지 않는다. 중간 페이지 실패와 취소 뒤에는 이전 완료 명단이 유지돼야 한다.

Facebook은 이 단계에서 `FORMAT_CHANGED`, TikTok은 `REAUTH_REQUIRED` 상태여서 마지막 정상값을 유지했다. 이는 두 개인 계정의 짧은 실기기 서비스 시험이며 모든 SNS의 연속 성공·24시간·자연 절전·팔로워 증감·실제 홈 위젯 반영을 검증한 결과로 확대하지 않는다. 실제 계정 값·세션·화면은 Git에 추가하지 않고 `.local/device-qa`에만 보관한다.


## Android Facebook 페이지 이동과 새 형식 — 2026-10-05

실제 세션에서 지정한 페이지의 이동을 검사했다. Facebook의 `intent://profile`에 공식 HTTPS 이름 주소 fallback이 있었지만 기존 정책이 `profile.php`만 허용해 차단했다. 정책 보완 APK를 데이터 보존 설치한 뒤 같은 페이지로 이동했고 `accepted=true`, `requestedPath=true`, 브라우저 안내 오류 없음까지 확인했다. 이는 페이지 저장 성공의 증거와 구분한다.

이후 데스크톱 표시의 읽기 진단에서 선택한 주소에 일치하는 `User`와 `delegate_page`를 확인했다. 기존 Page 전용 파서는 이 새 형식을 처리하지 못했다. 공개 화면과 해당 페이지의 소셜 정보에는 축약된 팔로워 라벨이 있었으며, 숫자 ID와 정확한 수의 확보가 추가로 필요한 상태였다. 실제 이름·URL·ID·수치·쿠키·원시 DOM은 Git에 추가하지 않는다.

최종 코드는 이름 주소 fallback, 새 페이지의 공개 프로필 ID/기반 페이지 구분, 같은 ID 조각의 정확한 수, 페이지에 연결된 소셜 라벨을 처리한다. 확인 버튼 이후에만 같은 공식 대상의 데스크톱 문서를 한 번 요청하고 제한된 로컬 재검사를 수행한다. 로그인과 개인 프로필 수집의 사용자 에이전트를 보존한다. 정확한 수가 없고 축약 라벨만 확인되면 그 한계를 별도 문구로 안내하며 연결이나 정확한 0으로 처리하지 않는다.
