# Facebook 페이지 연결

Android에서 개인 Facebook 프로필과 별도로 추적할 페이지를 연결한다. 관리 권한 확인을 대신하지 않으며, 사용자가 링크 또는 공식 Facebook 화면에서 선택한 페이지의 팔로워 수를 읽는다. iOS에도 같은 페이지 선택 흐름을 제공한다. Android는 연결 이후 반복 수집을 시도하며, iOS는 최초 네이티브 요청 검증에 성공한 페이지를 자동 수집 대상으로 삼는다. 실제 SNS·기기 성공 여부는 코드 검사와 구분한다.

## 사용 흐름

1. 계정 탭의 `SNS 연결`에서 `Facebook 페이지`를 선택한다.
2. `페이스북 페이지 링크`에 페이지 주소를 붙여넣고 **연결**을 한 번 누른다. `facebook.com/페이지주소`, HTTPS/HTTP 공식 주소와 `/share/<토큰>` 공유 링크를 받으며 HTTP는 HTTPS로 바꾼다. 로그인 전에도 이 버튼을 사용할 수 있다.
3. 로그인이 필요하면 아래 공식 Facebook 화면에서 로그인·추가 인증을 마친다. 정상 Facebook 화면으로 돌아오면 입력한 주소를 한 번 새로 연다. 로그인 전에 열었던 페이지를 그대로 새 관측으로 저장하지 않는다. 남은 쿠키가 있어도 실제 로그인·추가 인증 경로로 이동한 사실을 확인하며, 인증 화면에서 임의로 페이지를 다시 열지 않는다.
4. 일반 페이지 주소는 대상이 일치하고 페이지 ID·이름·정확한 팔로워 수와 인증 소유자를 확인하면 자동 저장하고 창을 닫는다. 별도 확인 버튼을 다시 누르지 않는다. ID를 알 수 없는 공유 링크는 열린 대상을 확인하고 **이 페이지 연결**을 한 번 누른다. Facebook 안에서 직접 찾은 페이지에도 같은 버튼을 사용할 수 있다.
5. 계정 탭과 위젯 계정 선택에서 `Facebook 페이지`와 페이지 이름을 확인한다. 상세 화면의 `페이지 열고 갱신`은 저장된 페이지와 주소를 열며 **연결** 또는 **이 페이지 연결**로 다시 수집한다.

페이지 창에서는 개인 프로필을 페이지로 자동 연결하지 않는다. 링크 제출마다 자동 확인은 한 번만 실행한다. 다른 페이지로 이동한 결과를 입력한 페이지로 간주하지 않으며 공유 토큰에서 페이지 ID를 추측하지 않는다. 여러 페이지를 각각 추가할 수 있으며 기존 페이지 갱신 중 다른 페이지로 이동하면 새 대상으로 덮어쓰지 않는다. 다른 페이지는 `SNS 연결`에서 별도로 추가한다.

Android에서 선택한 모바일 문서의 정보를 확보하지 못하면 같은 공식 페이지의 데스크톱 문서를 한 번 요청한다. 이때만 설치된 WebView 엔진 버전을 유지한 데스크톱 표시를 사용하고 이미지 로드를 막는다. 축약 표시가 먼저 나타나더라도 정확한 JSON·표시가 뒤늦게 준비되는지 최대 약 15초 동안 추가 SNS 요청 없이 같은 문서를 재확인한다. 원래 로그인 표시와 이미지 설정을 복원하고, 저장하는 로그인 정보에는 원래 사용자 에이전트를 사용한다. 요청 중 다른 페이지로 이동하면 연결하지 않는다. iOS는 페이지 문서에 데스크톱 표시를 적용하고 같은 문서의 준비 상태를 로컬에서 재확인한다.

Facebook이 축약된 팔로워 수만 제공하면 정확한 수를 만들지 않고 축약 표시 한계를 안내한다. 현재는 축약값을 연결·저장하는 기능을 제공하지 않는다. 페이지 식별 실패와 정확한 수치의 미확보를 서로 다른 문구로 안내한다.

## 수집·저장 경계

- 공식 HTTPS Facebook의 프로필 ID·페이지 주소, canonical/Open Graph·앱 링크 메타데이터와 해당 대상에 일치하는 `Page` JSON을 확인한다. 개인 프로필·홈·로그인·검색·게시물·그룹을 페이지로 저장하지 않는다.
- 숫자 ID가 하나로 확인되고 Page JSON, 유효한 페이지 메타데이터 또는 페이지 제목 주변 작은 헤더의 페이지 유형 표시가 있어야 한다. 대상과 관계없는 추천 페이지 JSON·다른 영역의 유형 표시·충돌하는 ID는 사용하지 않는다.
- 새 페이지 형식은 선택한 주소 또는 ID에 연결된 `User`와 유효한 `delegate_page.id`를 확인한다. 공개 프로필 ID를 추적 키로 사용하며 기반 페이지 ID와 혼동하지 않는다. 같은 공개 프로필 ID의 다른 User 조각에 있는 수치는 페이지 증거를 먼저 확보한 경우에만 사용한다. `people/.../<id>`와 `p/...-<id>` 주소도 ID를 확인하는 형식으로 처리하되 주소만으로 개인 프로필을 페이지로 판단하지 않는다.
- 정확한 JSON 팔로워 수 또는 페이지 제목과 함께 있는 작은 헤더의 정확한 팔로워 수만 사용한다. 두 정확한 값이 충돌하면 저장하지 않는다. 좋아요·친구 수·팔로잉·축약된 값은 팔로워 수로 대체하지 않는다. 정확한 0은 정상 수치다.
- 새 페이지의 소셜 정보에서는 같은 페이지의 공식 팔로워 링크에 연결된 정확한 라벨만 사용한다. 다른 페이지·팔로잉·외부 주소·인증 정보를 포함한 주소의 라벨은 사용하지 않는다.
- `accountType=PAGE`, 페이지 ID, 로그인 세션 소유자 ID를 구분한다. 개인 프로필의 기존 `FACEBOOK:<id>` 키는 유지하고 페이지에는 `FACEBOOK:PAGE:<page-id>` 키를 사용한다. 브라우저 출처는 `facebook-webview-page`, iOS 네이티브 응답 출처는 `facebook-page-session`이다.
- Android Room 버전 2→3은 명시적 마이그레이션으로 계정 provider 인덱스만 비고유 인덱스로 바꾼다. 부모 계정 테이블을 재생성하지 않아 기존 계정·수·명단·관계 이력 테이블과 기록을 보존한다. 개인 프로필은 여전히 SNS마다 하나만 허용하며 페이지만 여러 개 추가할 수 있다.
- 페이지 하나를 해제하면 그 페이지의 기록만 제거한다. 같은 SNS의 개인 프로필이나 다른 페이지가 있으면 공용 로그인 세션을 유지하며, 마지막 연결을 해제할 때 해당 SNS 세션을 정리한다.

브라우저로 확보한 최초 페이지 연결은 `FOREGROUND_ONLY`다. Android의 일반 15분 예약과 빠른 추적은 이 연결도 대상으로 삼는다. 수집 때 로그인 소유자는 `sessionOwnerId`, 대상은 페이지 ID로 각각 검증하고, 첫 확인에서 사용한 데스크톱 표시로 공식 페이지 문서 하나를 새로 요청한다. 로컬 정보 준비는 최대 15초 동안 추가 요청 없이 기다린다. 페이지가 바뀌거나 로그인이 만료·추가 인증 상태이면 저장하지 않는다. 서버 요청 제한과 계정별 재시도 기한도 지킨다. 실제 백그라운드 저장이 성공한 뒤에만 `background=OBSERVED`로 바꾼다.

빠른 추적 중에는 SNS마다 비활성 WebView 하나만 재사용한다. 연결 키·로그인 버전·페이지 주소·표시 설정이 달라지면 다시 만들며, 수집 후 문서를 비워 이전 페이지의 수치나 활성 스크립트를 남기지 않는다. 여러 페이지의 실패·요청 제한·기록은 각 연결 키로 구분한다. 페이지 팔로워 명단은 지원하지 않는다.

iOS는 페이지 ID와 로그인 소유자를 분리하고 개인 계정·페이지마다 기록을 보관한다. SQLite 버전 3은 기존 계정·수치·명단·관계 이력을 보존하면서 provider의 단일 연결 제약을 해제한다. 개인 프로필 하나 제한은 저장소에서 유지한다. 부모 테이블 교체 전 외래 키를 일시 해제하고 transaction 안에서 복사·교체·외래 키 검사를 수행하며 성공 후 다시 활성화한다. 페이지 한 개를 해제해도 같은 SNS의 다른 연결과 로그인은 유지하고, 로그아웃은 같은 SNS 전체에 적용한다.

iOS는 유효한 브라우저 수집 뒤 현재 세션·사용자 에이전트로 공식 페이지 문서를 한 번 새로 요청한다. 정확한 수와 같은 페이지 ID를 확인하면 `count=OBSERVED`, `background=UNVERIFIED`로 자동 수집을 허용한다. 예약·위젯에서 실제 새 관측을 저장한 뒤에만 `background=OBSERVED`가 된다. 초기 요청에 실패하면 원래 브라우저 수집값과 수집 시각을 유지하고 전경 갱신으로 표시한다. 서버의 기존·새 `Retry-After`는 지키며 대기 중 추가 요청하지 않는다. UI 문서 이동·창 닫기·로그아웃·세션 교체 뒤 늦은 응답은 저장하지 않는다.

네이티브 요청은 공식 HTTPS 페이지로만 최대 두 번 리다이렉트하며 최종 응답에서 원래 페이지 ID를 다시 검증한다. 전체 요청 시간·응답 크기·JSON 탐색량을 제한하고 취소는 전파한다. 스크립트는 실행하지 않고 구조화 JSON만 읽는다. 이름 주소와 ID의 결합을 먼저 확보한 뒤 같은 ID의 분리된 JSON 조각을 사용하며 추천 페이지·개인 프로필·다른 페이지·축약/충돌 수치는 거부한다. 브라우저의 헤더 표시에서만 수를 제공하는 페이지는 네이티브 경로로 자동 승격하지 않는다.

iOS 작은 위젯은 실제 연결 ID로 개인 계정이나 페이지를 고를 수 있다. 이전 위젯의 SNS 선택값은 호환 경로로 유지하며 선택한 페이지를 해제하면 다른 계정으로 자동 대체하지 않는다. 동적 선택은 [Apple의 구성형 위젯 안내](https://developer.apple.com/documentation/widgetkit/making-a-configurable-widget)를 따른다. iOS의 일반 요청 간격은 15분이고 실제 실행은 OS가 결정한다. 이 경로를 1분 갱신이나 실제 페이지 백그라운드 수집의 검증 완료로 취급하지 않는다.

## 검사

`FacebookPageConnectionRequestTest`와 Swift의 같은 정책 검사는 링크 제출, 로그인·추가 인증 보류와 한 번의 대상 복귀, 로그인 전 문서 새로 열기, 다른 대상·잘못된 주소 거부 및 공유 링크의 최종 확인을 검사한다. `FacebookPageLinkRuntimeTest`는 빈 `dev.datell.followertracker.loginvalidation` 패키지만 허용한다. 합성 쿠키와 네트워크가 차단된 로컬 문서로 링크 제출 한 번의 연결·정확한 0·중복 저장 방지·인증 복귀·다른 페이지 거부·공유 링크 확인·남은 쿠키의 로그인 이동·로그인 전후 새 문서·축약 표시 뒤 정확한 수치 준비를 확인한다. 개인 세션이 있는 앱에는 실행하지 않으며 계정 DB에 시험 값을 저장하지 않는다. UI 검사의 컴파일과 실제 실행 결과는 구분한다.

공통 Node 검사는 페이지와 로그인 소유자 분리, 명시적 페이지 경로, 외부 주소·개인 프로필·추천 페이지 거부, 정확한 0, 축약·충돌 수치 및 기존 개인 캡처 보존을 검사한다. Android 핵심 검사는 캡처 계약·소유자·대상 ID·정밀도·공식 URL과 기존 계정 JSON 호환성을 검사한다.

`FacebookPageConfirmationRuntimeTest`는 기존 Facebook 세션을 읽기 전용으로 사용하는 HTTPS fixture다. 버튼을 누르기 전 연결하지 않는 동작, 정확한 페이지 수집, 축약 수치·개인 프로필 거부를 검사하며 계정 DB나 쿠키에 시험 값을 저장하지 않는다. 기존 인증 세션이 없는 기기에서는 실행을 보류한다. `FacebookPageStorageRuntimeTest`는 별도의 Room DB로 다중 페이지 기록·해제와 버전 2 업그레이드 보존을 검사한다.

`FacebookPageDiagnostic`는 `probeFacebookPageUrl`로 명시한 공식 HTTPS 페이지를 기존 세션으로 열어 구조·수집 성공 플래그만 출력한다. 원시 DOM·쿠키·계정명·ID·수치는 출력하지 않으며 실제 연결을 저장하지 않는다. 실제 앱의 버튼 연결·저장은 별도 확인해야 한다. 실제 시험 결과와 미검증 항목은 [기기 검증](DEVICE_VALIDATION.md)에 기록한다.

`probeFacebookConfirmation=true`는 실제 확인 버튼과 같은 제한된 읽기 함수를 사용한다. `probeFacebookDesktop=true`는 표시 형식을 비교하는 별도 읽기 진단이다. 어느 진단도 계정 DB나 세션에 시험 값을 저장하지 않는다. 데스크톱 진단 완료와 실제 앱의 연결·저장 성공을 구분한다.


## 2026-10-21 코드·기기 검증 범위

- Android core 45개·app Debug/Release 각 106개, 공유 캡처 63개를 통과했다. 개인 프로필과 여러 페이지를 함께 24시간 가상 실행해 한 페이지의 429·다른 페이지의 추가 인증이 개인 계정의 1분 수집을 막지 않는지 검사했다. 실제 SNS 24시간 수집 결과는 아니다.
- 별도 `dev.datell.followertracker.pagevalidation` 앱의 WebView 회귀 5개를 실제 Android 기기에서 통과했다. 반복 수집·다른 페이지 전환·로그인 소유자 불일치·페이지 바뀜·늦은 문서 준비·실제 로그인 및 추가 인증 경로를 검사했다. 합성 쿠키·문서는 이 검증 앱에만 넣고 네트워크를 차단했다. 최초 실행의 지연 문서 fixture는 인증 확인에서 실패했고, 쿠키 설정 완료를 기다리고 외부 요청을 차단한 최종 fixture로 다시 통과했다.
- Swift core 57개, 실제 SQLite 저장소·SyncService의 macOS 검사 18개를 통과했다. 후자의 Keychain·네트워크 상태는 대역이며 iOS 기기 검사가 아니다. 버전 1·2 기록 보존, 여러 페이지 기록과 개별 위젯 조회·연결 해제 경계를 검사했다.
- Android Debug·테스트 APK·Release/R8·Debug/Release lint를 통과했다. iOS 페이지 확인과 대상 불일치 UI 회귀는 테스트 타깃으로 컴파일했으며 실제 WebKit UI 실행은 아직 하지 않았다.

## 2026-10-22 iOS 네이티브 페이지 요청 검증

기존 iOS 수집기는 Facebook 페이지도 네이티브 요청 전에 전경 전용으로 종료했다. 페이지 전용 HTTP·구조화 JSON 판독을 연결하고 최초 브라우저 연결 뒤 네이티브 검증을 추가했다. 페이지 ID·로그인 소유자·기록 키와 연결 시각을 유지한다. 초기 HTTP 실패는 실제 브라우저 값과 관측 시각을 그대로 남기며 성공한 것처럼 새 시각을 만들지 않는다.

iOS Debug 검사 타깃과 서명 없는 Release 앱·위젯 빌드가 통과했다. 같은 공유 검사를 `swift test --package-path ios`와 CI에서 재현하도록 추가했으며 macOS 대역은 앱·위젯 프로젝트에서 제외한다. 실제 iOS 로그인·페이지 HTTP 응답·OS 예약·홈 위젯과 Android 새 페이지 APK 설치는 기기 미연결로 실행하지 못했다. 네이티브 경로 구현을 실제 SNS 지원 검증 완료로 취급하지 않는다.
