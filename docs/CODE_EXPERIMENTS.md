# Android 수집 루프 코드 실험

2026-10-18. 실기기 장시간 관찰보다 코드의 반복·실패·복구 경계 검증을 먼저 진행한다. 앞서 연결한 24시간 관찰 자동 점검은 중지했다.

`RapidTrackingService`가 실제로 실행하는 루프를 `CountTrackingLoop`로 분리했다. 서비스에서는 실제 단조 시계·저장소·수집기·네트워크 callback·지연을 연결한다. JVM 실험에서는 같은 루프에 가상 시계와 메모리 저장소를 연결한다. 테스트만의 별도 반복 알고리즘을 만들어 실제 서비스 대신 검사하지 않는다. 휴대폰·실제 SNS·HTTP·쿠키·앱 DB는 사용하지 않는다.

## 반복·실패 실험

다섯 SNS는 Instagram·TikTok·X·Facebook 개인 프로필·Reddit의 합성 계정이다. 아래 시간과 수집 횟수는 가상 실행 결과다. 실제 SNS 지원이나 해당 시간만큼의 실기기 실행 성공을 뜻하지 않는다.

| 연결 없음·모든 계정 인증 만료 | 빈 성공 주기나 무한 재시도 대신 명시적인 종료 |

16개 수집 루프 검사와 8개 복구 검사, 총 24개가 통과했다. 복구 검사는 일반/중지된 세션의 거부, 정상 실행 중 재시작 생략, 복구 요청 전달과 실제 실행의 구분, OS 거절 시 의사 보존과 재시도 횟수 제한, 중지 경합, 늦게 전달된 복구 요청의 거부, 취소 전파, 가상 24시간 중 사용자 중지 뒤 재시작 방지를 검사한다.

## 실험에서 재현하고 고친 문제

기존 동작을 그대로 옮긴 루프에 처음 추가한 13개 중 다음 두 개가 실패했다. 실패 결과를 보존하고 실제 서비스가 사용하는 루프를 수정한 뒤 같은 검사를 통과했다.

- 429 대기 계정의 내부 수집 전달 횟수는 가상 하루 1,426회여야 하지만 1,440회였다. 하위 수집 정책이 HTTP 요청은 막고 있었으나 기한 전에도 저장소·수집기까지 호출했다. 루프에서 `RefreshPolicy.canRefresh`를 적용해 기한이 된 계정만 전달한다.
- 다른 계정이 모두 재로그인 상태이면 그 계정들의 빈 대기 시각이 정상 대기 계산을 덮었다. 10분 기한을 가진 유일한 재시도 계정을 9분간 관찰할 때 전달이 0회여야 하지만 9회였다. 대기 계산에서 자동 재시도할 수 없는 계정을 제외해 실제 다음 기한까지 한 번 기다린다.

이 횟수는 코드 실험의 내부 호출 수다. 실제 데이터·배터리 절감률을 측정한 수치로 사용하지 않는다.

## 복구의 완료 경계

프리미엄 실행 요청이 남은 경우에만 복구를 요청한다. 복구 요청 자체는 새로운 사용자 시작으로 취급하지 않으며 기존 실행 식별자·시작 시각을 재사용한다. 중지 요청을 먼저 확인해 늦게 전달된 복구 intent도 거부한다. 예상 밖 중단과 OS의 재시작 거절은 사용자가 중지한 것으로 바꾸지 않는다. 실제 서비스가 시작되기 전에 실행 중이나 새 수집 성공으로 표시하지 않는다.

명시적인 프리미엄 시작 시 최초 1분 뒤 점검과 15분 주기의 보조 점검을 등록한다. 정상 서비스가 실행 중이면 SNS 요청이나 재시작을 하지 않는다. 최초 복구 요청의 OS 거절은 최대 세 번의 시도로 제한하며 사용자의 실행 요청은 보존한다. 중지 버튼·중지 알림·계정 없음은 요청과 보조 예약을 취소한다. 2026-10-19 보완에서 모든 계정의 인증 만료는 실행 요청을 보존하며 다시 연결할 때까지 서비스를 시작하지 않도록 구분했다. 사용자가 로그아웃해 대상이 모두 없어지면 요청을 취소한다. 작업 저장소 취소 실패가 실제 서비스 중지를 막지 않으며, 나중에 도착한 복구 요청도 중지된 의사를 다시 확인한다. Release나 중지된 상태의 앱 시작은 남은 시험용 보조 예약을 취소한다. 일반 15분 수집과 명단 예약은 유지한다.

복구 요청은 OS의 실행 허용을 보장하지 않는다. Android 12 이상은 백그라운드의 전경 서비스 시작을 제한하며, 이 예외 경로도 코드 실험에서 검사한다. 강제 중지·재부팅·보호 설정을 우회하지 않는다. 이번 코드 변경의 실제 OS 프로세스 재기동은 아직 검증하지 않았다. [Android 백그라운드 시작 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

## 재현 명령

저장소의 JDK 21·Gradle 설정을 사용한다.

```sh
cd android
./gradlew :app:testDebugUnitTest \
  --tests '*CountTrackingLoopExperimentTest' \
  --tests '*TrackingRecoveryExperimentTest' --no-daemon
./gradlew :core:test :app:testDebugUnitTest :app:testReleaseUnitTest \
  :app:assembleDebug :app:assembleDebugAndroidTest :app:assembleRelease \
  :app:lintDebug :app:lintRelease --no-daemon
```

첫 명령은 코드 실험만 실행한다. 두 번째 명령은 기존 동작·Release와 APK·기기 검사 코드 컴파일·lint까지 확인한다. 전체 사용자 기기의 instrumentation이나 실제 SNS 요청을 실행하는 명령이 아니다.

로컬 최종 결과는 core 45개·app Debug 76개·app Release 76개가 실패·skip 없이 통과했다. Debug·테스트 APK·Release/R8 빌드와 두 lint도 통과했다. lint 오류는 0개이며 기존 경고는 각각 8개다. 의존성·잠금·DB 스키마·일반 15분 간격은 바꾸지 않았다. 이 수정본을 휴대폰에 재설치하거나 실기기 장시간 관찰을 재개하지 않았다.

## 2026-10-19 수명주기·복귀 신호·로그아웃 보완

앱 시작의 복구 예약 누락, 예상 밖 하위 취소 후 실행 상태 잔류, 인증 대기 중 불필요한 재시작의 세 실패를 재현하고 고쳤다. 앱 복귀·세션 변경 신호와 네트워크 callback 누락 재확인을 추가했으며, 조기 깨움이 매초 수집을 만들던 실패도 재현하고 계정별 단조 시계 간격으로 막았다. 기존 가상 24·72시간 실험을 유지하며 Android app은 Debug/Release 각 99개를 통과했다. 실제 SQLite의 늦은 로그아웃 결과 실험과 기기 미실행 범위는 [지속 수집·로그아웃 검증](CONTINUITY_AND_LOGOUT.md)에 기록한다.
