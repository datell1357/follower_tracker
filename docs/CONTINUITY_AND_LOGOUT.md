# 지속 수집 복구·로그아웃·소형 위젯

2026-10-19. 사용자의 코드 우선 요청에 따라 기기·실제 SNS와 분리해 수정하고 검사했다. 이 문서의 코드·저장 실험을 실기기의 장시간 수집 성공으로 해석하지 않는다.

## 수집이 중단될 수 있던 경로

| 코드 경로 | 기존 동작 | 변경 |
| --- | --- | --- |
| 프로세스 재생성 | 실행 요청이 남아도 복구 작업을 다시 등록하지 않음 | 요청이 남은 프리미엄 시험만 최초·정기 점검 재등록 |
| 루프의 예상 밖 취소 | 코루틴은 끝났는데 실행 상태가 true로 남을 수 있음 | 명시적 중지와 구분해 실행 상태를 내리고 복구 요청 유지 |
| 오프라인 대기 | 등록한 네트워크 callback이 오지 않으면 계속 대기 | 앱 복귀·세션 변경 신호로 깨우고 callback 누락 시 5분마다 연결 상태만 재확인 |
| 긴 재시도 대기 | 새 계정을 연결하거나 로그인해도 기존 대기를 기다림 | 변경 신호로 다음 실행 조건 재계산 |
| 앱 복귀의 위젯 갱신 | 기존 소형 provider만 갱신 | 두 provider 모두 갱신, 개별 실패 격리 |

앱 재진입과 로그인 성공 뒤에는 남아 있는 프리미엄 실행 요청을 복구한다. Debug manifest에만 재부팅 완료·앱 업데이트 receiver를 등록한다. 계정이 모두 인증 만료 상태면 요청을 보존하고 연결을 기다리며 빈 서비스를 반복 실행하지 않는다. 앱의 중지 버튼·알림 중지·사용자 로그아웃으로 대상이 모두 사라진 경우에는 요청을 해제한다. 일반 모드의 시간 제한·Release의 `dataSync`·일반 예약 15분은 그대로다.

복구는 실제 서비스가 시작되기 전까지 실행 중으로 표시하지 않는다. 복구 때문에 시작 시각이나 세션 식별자를 새로 만들지 않는다. Android의 백그라운드 시작 거절은 최대 세 차례 시도하고 다음 정기 점검으로 넘긴다. 재부팅·업데이트와 사용자에게 보이는 Activity의 시작 예외는 [Android 공식 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)을 따른다. OS가 강제 중지한 상태의 실행이나 실제 기기에서의 24시간 연속 수집을 보장한 결과는 아니다.

앱 복귀 신호가 자주 와도 SNS를 연속 요청하지 않도록 계정별 마지막 전달 시각을 단조 시계로 관리한다. 서버 `Retry-After`와 로컬 재시도 기한도 함께 지킨다. 새 계정은 다른 SNS의 긴 대기에 묶이지 않는다. 전경 알림이 살아 있다는 사실과 새 관측 저장을 구분한다.

## 로그아웃과 연결 해제

| 동작 | 로그인 정보 | 기존 계정·수치·관계 기록 |
| --- | --- | --- |
| 로그아웃 | 해당 SNS의 이 기기 로그인 제거 | 유지, 다시 로그인 필요 상태로 전환 |
| 연결 해제 | 마지막 연결이면 해당 SNS 로그인도 제거 | 선택한 연결의 기록 삭제 |

계정 상세와 설정의 연결 관리에서 로그아웃을 실행할 수 있다. 같은 SNS가 공용 세션을 쓰므로 Android의 Facebook 개인 계정과 페이지도 함께 적용한다. 다른 SNS는 유지한다. 개인 계정을 바꾸는 경우의 기존 한 SNS당 개인 계정 하나 계약은 바꾸지 않는다.

Android는 세션 메타데이터를 먼저 무효화하고 진행 중인 해당 SNS의 프로필 브라우저만 취소·정리한 뒤 쿠키·웹 저장소를 비운다. 취소된 하위 읽기가 전체 수집 루프를 끊지 않으며 부모의 중지 취소는 계속 전파한다. iOS는 공유 Keychain에 로그인 변경 때만 갱신하는 무작위 버전을 두며 일반 응답 쿠키 갱신은 그 버전을 바꾸지 않는다.

수치·실패 상태 복원·명단을 쓰는 DB transaction 안에서 요청 당시 세션 버전을 다시 비교한다. 로그아웃·새 로그인 뒤의 늦은 결과는 계정을 다시 READY로 바꾸거나 새 관측·명단을 추가하지 못한다. 계정 ID·연결 시각·기록과 DB 스키마를 바꾸지 않는다.

## 작은 위젯

1×1의 로고·여백을 줄여 계정명, 팔로워 수, 직전 증감, 팔로잉 수, 실제 수집 시각을 우선한다. 팔로잉 수가 없는 SNS에는 실제 직전 팔로워 수를 표시하며 0을 만들지 않는다. 아주 작은 호스트에서는 수와 실제 시각을 우선하고, 확장 크기에서는 비교 기준 시각과 상태도 표시한다. 앱 위젯 탭의 큰 표어·중복 설명 패널과 과한 미리보기 여백도 줄였다. 수집·전체 이력 조회·주기 타이머를 추가하지 않는다.

## 코드 검증

- 수명주기 검사 7개 중 세 실패를 재현한 뒤 수정했다. 기존 실행 요청의 복구 예약 누락, 예상 밖 취소 뒤 상태 잔류, 연결 불가 상태의 서비스 재시작이다.
- 대기를 조기 해제하는 실험에서 매초 신호가 오면 요청도 매초 반복되는 실패를 먼저 재현했다. 수정 후 3분 동안 다섯 SNS 각각 0·60·120초에만 전달한다. 기존 가상 24·72시간 실험·요청 제한·명시적 중지·취소도 유지한다.
- Android core 45개, app Debug/Release 각각 99개가 실패·skip 없이 통과했다. Debug·테스트 APK·Release/R8·두 lint도 통과했고 lint 오류 0개·기존 경고 각 8개다.
- Swift core 50개와 iOS Debug `build-for-testing`·Release 서명 없는 빌드를 통과했다. iOS 시뮬레이터는 실행하지 않았다.
- 공유 수집 스크립트 회귀 60개도 통과했고, iOS 프로젝트를 재생성해 기존 프로젝트와 동일함을 확인했다.
- 실제 공유 `TrackerRepository`·`SyncService`와 기존/새 XCTest를 macOS의 별도 패키지에 연결해 SQLite 저장 실험 16개를 통과했다. 새 로그아웃 검사는 성공·수집 실패·저장 실패·취소의 늦은 결과, 기존 수치와 관계 비교·다른 SNS 보존을 확인한다. Keychain·암호화·네트워크 상태는 이 실험에서 대역이며 실제 자격 증명·App Group DB·SNS를 사용하지 않는다. iOS 런타임 전체나 실제 Keychain 검증이 아니다.
- 이 실험에서 기존 형식 오류 fixture의 실패도 기준 커밋으로 재현했다. 실제 정책이 저장하는 15분 재시도 시각이 빠져 있었다. 기존 차단 assertion을 유지하면서 fixture에 기한을 넣고 만료 뒤 다시 읽는 검사도 추가했다.
- Android의 로그아웃 저장 경쟁·다른 SNS 지속과 새 소형 표시 검사는 instrumentation으로 추가하고 컴파일했다. USB 기기 없이 실행하지 않았으며 화면·쿠키 정리·서비스 재시작·실제 SNS 후속 수집은 다음 실기기 검증 범위다.

```sh
cd android
./gradlew :core:test :app:testDebugUnitTest :app:testReleaseUnitTest \
  :app:assembleDebug :app:assembleDebugAndroidTest :app:assembleRelease \
  :app:lintDebug :app:lintRelease --no-daemon
```

격리 실험의 harness·OS 대역·로그와 APK는 `.local/device-qa/continuity-20261019/`에 보관하고 Git에 포함하지 않는다. 사용자 계정·세션·기록을 변경하거나 장시간 자동 감시를 재개하지 않았다.
